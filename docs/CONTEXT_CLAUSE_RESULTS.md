# 文節単位の文脈評価への変更

2026年10月15日。利用者の長文対応の実装依頼に基づき、E:/prog/Meltype/Tools/context-evaluationで実装・検証した。PCへのインストールと外部公開は行っていない。

## 変更内容

controllerは全文候補を最大32個並べる処理を廃止し、既存変換器が返す各文節の候補を個別に評価する。出力する読みと候補は64文字まで、候補5個。英語と保護区間は固定し、左256文字・右128文字の文脈を参照する。文章全体の100文字制限をcontroller経路から除いた。

180ms待機後、1入力世代につき1500ms以内で順に評価する。複数箇所の結果は一括表示し、期限切れでは既に得た結果だけを反映する。古い入力の結果、候補外の文字列、手動選択後・確定後・取消後の結果は適用しない。自動補正は新しい予測履歴へ記録しない。旧全文APIは以前の対照実験用として残す。

実Googleでの長文検証では、変換器自身の100文字制限も見つかった。全体は512文字まで受け付け、Googleへは100文字以内の窓で要求する。中間窓が複数文節なら最後の文節を次へ残して読み直す。全窓で2秒期限を共有し、読み一致確認・1MB応答上限・専用セッションの破棄を維持した。途中で失敗したら部分的な変換を返さず、入力の欠落を防ぐ。Googleへの学習要求は従来の100文字上限を維持する。

20/50文字は意味の手掛かりが未完成のため未採点。新方式のモデルHTTP要求は全101段階で106回、例外0、応答は全て候補内。400文字でも生成する文字列は先頭の短い対象語だけで、後続は固定される。400文字の値が200文字より速いのは参照範囲とキャッシュの影響を含み、長文ほど高速になるという意味ではない。測定は単回で、CPU負荷も完全には統制していない。

精度自体は改善していない。革を川に変える例と、厚い本を暑いままにする例が残る。基準候補4/8から3例を改善し、1例を悪化させて6/8になった。日常入力の正解率として扱わない。

2箇所を同時に直す系列では、200/400文字で「橋と川」を「箸と革」へ補正できた。50/80/100文字では両方の正解を選べなかった。候補の組合せがないという構造上の制限は解消したが、モデル判断の誤りは残る。

左文脈の手掛かりの後ろに128文字を挟む条件は5/8正解。256文字以上を挟むと手掛かりが送信範囲から外れ、4/8となった。文章のどこでも参照できる機能ではない。

analyze_clause_results.pyでsamples.jsonlとresults.jsonの全行一致、101件のID一意性、出力が各文節候補を合成したものか、全要求の読み・候補64文字以内と文脈256/128以内、正解集計を照合しsummary.jsonへ保存した。

## 制限

主な精度比較は手作業の候補と文節区切りを使う8意味例。人間の使用感、長時間のメモリ増加、多数のアプリでの入力、GPUは未検証。1文節が64文字を超える場合は評価せず、文節数が多い場合は1500msの予算に収まった先頭側だけが評価される。Googleが受け取れる未確定日本語区間は512文字まで。確定済み文章の右側をNative hostから新しく取得する処理は追加していない。

新方式の再実行はtools/context-eval/Run-ContextLengthExperiment.ps1 -Clauses、実GoogleとTSFは-Native。事前にsrc/Meltype.Testsをビルドする。実行ごとに別ディレクトリーへ保存し、起動したモデルサーバーだけを停止する。

主な回帰証跡はexperimental-build/context-clause-final-regression.log、context-clause-google-regression.log、context-clause-unit.log。実Googleへの直接変換はtools/context-eval/Test-LongGoogleConversion.ps1で再実行する。
