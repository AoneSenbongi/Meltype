# Windows検索欄への対応調査

## 目的と確認済みの原因候補

検索欄でもMeltypeの日英判別とGoogleライブ変換を使えるようにする。2026年10月7日の読み取り専用診断では、このPCのSearchApp.exeはAppContainer、整合性レベルLow（4096）だった。MeltypeNative64.dllは読み込まれていなかった。ただし検索欄にフォーカスした状態の操作記録はまだないため、DLLがないことだけで直接の失敗箇所を確定しない。

現行ソースはHKCUのCOM登録、ユーザーフォルダー内のDLL、通常ユーザー限定パイプを使い、IMMERSIVESUPPORTを登録していない。AppContainer向けのIMEロード・アクセス・通信に対応していない。単に対応フラグを追加しても通信とDLLアクセスが解決するとは限らない。

根拠はMicrosoftのIME要件と実ソース。検索用APIによる候補の統合表示は、検索欄で通常の変換を使うための初期対応と分ける。
https://learn.microsoft.com/en-us/windows/apps/develop/input/input-method-editor-requirements

## 試作前の確認事項

隔離した試験用AppContainerで、現行DLLのファイル読み取り・DLLロード・現行通信権限での接続がAccess Denied（5）になることを再現した。試験用プロファイルと実行ファイルは削除済み。次はこの再現テストを基に修正する。テストは固定の文字列だけを使う。検索語や個人の入力履歴は取得しない。導入済みIMEの登録と配置は変更しない。

試作では対応カテゴリ・ITfTextInputProcessorEx、保護されたDLL配置、検索アプリに限定した通信権限を検討する。参考ForkはAppContainerでサーバー確認を省略する場合があるが、その処理をそのまま採用せず、現行の通信先確認を維持できる方式を試験する。必要な権限とアクセス先を明記してからユーザーへ共有する。

Program Filesへの配置やHKLM登録を採用する場合は、既存HKCU登録からの切替・取消時の復旧・削除も同時に設計する。Google本体や辞書・学習データの保存先は変更しない。登録・インストール済みIMEの変更前には具体的な内容と復旧方法を示して承認を受ける。

## 完了条件

検索欄で日本語・英語混在、ライブ変換、Spaceの候補選択、句読点、EnterとEscapeが動作する。通常のデスクトップアプリも回帰試験が通る。接続権限を与えていないAppContainer・別ユーザー・偽サーバーを拒否する。実機操作確認まで終わる前に対応済みと記載しない。GitHubへのpush・Issue・Releaseは別途確認を受けてから行う。

## 通信先確認の追加試験

次の隔離試験では、AppContainerから通常権限の試験プロセスとトークンを照会できるか確認する。既存の通信先確認は、接続先のユーザーと整合性レベルを照合するため、この照会権限も必要になる。試験用の一時プロファイルにだけ、試験プロセスの限定照会と試験トークンの読み取りを許可した場合を比較する。導入済みサービス・検索アプリの権限やIME登録は変更しない。結果を見てから製品の方式を決める。

2026年10月7日、既定ではプロセス照会がAccess Denied（5）になることを確認した。一時プロファイルのSIDへPROCESS_QUERY_LIMITED_INFORMATIONとTOKEN_QUERYを許可した場合は両方の照会が通過した。権限を付与したのは終了時に消える試験用プロセスとトークンだけ。

次の接続試験では、試験用パイプの所有ユーザーと特定の一時プロファイルだけにアクセスを許可する。パイプはLowからの書き込みを許可し、AppContainer側のアクセス要求からサーバーの追加作成権限を除く。許可対象のAppContainerは接続でき、別のSIDにしか許可していないパイプには接続できないことを確認する。実入力の送信と製品への導入は行わない。

2026年10月7日、限定されたAppContainerでパイプ接続・接続先のプロセス照会・トークン照会が成功した。別のSIDしか許可されていないパイプへの接続と、許可クライアントによる追加サーバーの作成はAccess Denied（5）だった。`Test-NativeSearchPeerAccess.ps1` で4ケースを検証済み。これにより通信先の確認を省略せずに接続できる方法を確認した。ただし製品サービスへの組み込み・DLLの配置変更・検索欄での実入力は未実施。

## 組み込み方針

今回の対応先は、このPCで確認したWindows 10の検索パッケージ `Microsoft.Windows.Search_cw5n1h2txyewy` とする。パッケージSIDはOSのAPIで導出する。ほかのAppContainerへ一括で通信権限を与えない。Windows 11の検索欄は別途確認する。

サービスは所有ユーザーと検索パッケージにだけパイプへのアクセスを許可する。検索パッケージには追加サーバーの作成を許可しない。接続後もクライアントのユーザーを確認し、検索パッケージ以外のAppContainerと通常のLowプロセスを拒否する。サービス側のプロセスとトークンには、検索パッケージの限定照会・読み取りだけを追加する。送信前のDLLによる通信先確認は維持する。

DLLはITfTextInputProcessorExに対応し、対応カテゴリを登録する。管理者操作でProgram Files配下の保護された版別フォルダーへ配置し、HKLMのCOM登録へ切り替える。成功後にこのCLSIDの旧HKCU登録を解除する。更新・削除も登録方式に合わせる。移行失敗時は新登録を解除し、旧DLL・旧登録・旧設定へ戻す。旧版と辞書のバックアップを保持する。実際の配置・登録・サービス再起動はユーザー承認後に行う。

## ローカル実装と検証結果

2026年10月7日、上記の限定通信、ITfTextInputProcessorExとIMMERSIVESUPPORT登録、保護された版別配置、更新・自動起動・削除の登録方式切替を実装した。管理ルートはユーザー別のInstallRootで保持し、Program FilesのDLL配置先とは分ける。マニフェストは管理者起動前のハッシュと照合し、コピー後にも各ファイルのハッシュと所有者・書き込み権限を確認する。旧DLLは上書きしない。

製品のDLLと変換サービスを使う隔離AppContainer試験では、双方の接続先確認、固定入力nihongoのライブ変換、Spaceによる候補取得、Enterによる日本語確定が通過した。学習は無効にしている。別パッケージの拒否、追加サーバー作成の拒否、同名パイプ占有の拒否も確認した。結果はTest-NativeSearchTransport.ps1とexperimental-buildのsearch-transport-result.json、search-google-conversion-result.jsonを参照する。

通常のGoogle・TSF文書試験、候補一覧の再描画、管理画面と更新判定も通過した。管理者確認の取消、登録状態が不明な失敗、更新後の起動失敗について、実際の更新スクリプトを隔離した依存先で実行し、旧設定・旧登録方式・自動起動・旧サービスの復旧を確認した。管理者ヘルパーの結果が返らない場合も登録状態を不明として復旧を要求する。

2026年10月7日、ユーザー承認後にこのPCへ適用した。Program Filesへの実配置と保護ACL、HKLM登録の一致、旧HKCUのCOM登録解除、全ペイロードのハッシュ、変換サービスの起動と自動起動を確認した。新サービスへの通常のGoogle・TSF試験も通過した。Windows検索アプリは終了しておらず、ユーザーが検索欄で入力できることを確認した。全キー操作と候補UIは未確認。検索対応は未公開の試験版であり、公開済み1.0.2が対応済みという意味ではない。

## 通信枠が埋まった場合

通信パイプの上限は待受を含め32インスタンスとする。上限に達した場合のエラー231だけは100ms待って再試行し、サービスを終了しない。停止要求で待機を中断する。同名占有・アクセス拒否などのエラーは従来どおり失敗とし、接続先確認と権限を緩めない。入力文字や辞書の記録を追加しない。
