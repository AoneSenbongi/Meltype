# 文脈によるライブ変換評価の試作

## 目的

Meltypeの日英自動判定とライブ変換を保ち、後続入力を含む未確定文章の候補をローカルzenzで選び直す。導入そのものを目的にしない。PCへの適用・外部公開は今回の対象外。

## 現在の実装範囲

### 文節ごとの文脈評価

2026年10月15日の長文測定に基づき、controllerのモデル評価を文節単位に変更した。既存変換器の文節とキャッシュ候補を使い、候補を持つ各文節の読み・候補だけを出力対象とする。左256文字・右128文字までを文脈として参照し、全文の100文字制限と全文候補32通りの組合せはcontroller経路から除いた。1文節の読み・候補は64文字以内、候補は5個以内、変更する文字列は既存候補に限定する。

入力停止後180msで開始し、順番に評価する。1回の入力世代全体の期限は1500ms。時間切れなら完了済みの採用結果を反映し、残りはその時点の表示を保持する。複数箇所の変更は一括で表示する。入力・文脈変更・手動選択・確定・取消で未完了要求を中止し、古い結果を適用しない。同じ文脈で読みと基準表記が変わらない先頭文節は、次回の評価中も既採用候補を保持する。固定された英語区間と保護区間は評価しない。自動判断を履歴へ学習しない。

実Googleで147/377文字を入力する検証では、変換器自身の100文字入力制限も見つかった。入力全体は512文字まで受け付け、Googleへは100文字以内の窓で要求する。途中の窓では、複数文節なら最後の文節を次の窓へ残す。全窓で共有する2秒期限、応答1MB上限、読み一致確認、専用セッション破棄を維持し、窓のいずれかが失敗した場合は不完全な変換を返さない。Googleへの学習要求は従来の100文字上限を変更しない。

ContextEvaluationの旧全文APIは先行比較実験のために残し、controllerは専用のClauseContextEvaluationを使用する。モデルpromptの文脈参照幅は新しい256/128へ変更したため、旧レポートの数値は当時の条件として扱う。比較と検証はdocs/CONTEXT_CLAUSE_RESULTS.md。通常のPC環境へは未適用。

- 既存変換を即時表示し、短い待機後に文節候補を非同期評価する。候補一覧を文法制約にし、一覧外の文字列を採用しない。
- 日本語の読みと候補、英語・保護区間、確定済みの左文脈、取得できる右文脈を区別する。同じ未確定入力内の後続部分は右文脈に含む。
- 英語・URL・コードは候補生成時に固定する。手動候補選択後、F6〜F10、再変換、予測選択中は自動補正しない。初期実装ではその未確定入力全体を保護する。
- 入力・文脈変更、取消、確定、フォーカス変更後に届いた結果を捨てる。Enterは画面に表示中の値を確定する。LLM結果だけを無条件に学習させない。
- Native版は実験用の環境変数で明示的に有効化する。既定は無効。既存のユーザー設定・辞書・履歴を実験で変更しない。
- 初期実装では既存エンジンが提示できる候補の選び直しに限定し、LLMによる新語生成や文節の再構成は行わない。候補に正解が無い問題は別に計測する。

## 比較方法

合成した打鍵・候補選択・確定・取消の列を同じ条件で再生する。学習なし、全確定を記録、明示修正のみ、文脈別の明示修正を比較する。学習は実験専用のメモリに保持し、製品の履歴には保存しない。

学習用と評価用の文章を分ける。同じ読みで異なる意味になる文脈、入力途中から意味が明らかになる文、日英混在、URL、誤確定後の取消、過去の好みが別文脈へ波及する例を含める。採点は既知の正解との一致を主とし、LLM自身の採点を正解としない。

報告する値は正解率、候補内に正解がある割合、既存の正解を崩した数、表示変更、モデル応答時間、実行環境。合成データの結果を実利用の品質や主観的使用感と同一視しない。表示変更は打鍵による自然な文字追加と区別する。

今回比較するのは外部の履歴適用方式で、zenzの重みは更新しない。学習用の`expected`は、そのイベントで確定された表記を示し、意図的な誤確定も含む。評価用の`expected`は人手で定義した正解とする。取消されたイベントは学習へ反映しない。

4方式の定義は以下のとおり。

| 方式 | 記録 | 再利用 |
| --- | --- | --- |
| none | なし | 毎回モデルで評価 |
| all-commits | 全確定の回数 | 同じ読みで最多の表記をモデルより優先 |
| explicit-only | 明示修正の回数 | 同じ読みで最多の表記をモデルより優先 |
| contextual-explicit | 明示修正の回数 | 読み・左文脈・右文脈が完全一致した場合だけ再利用 |

文脈別方式は意味の似た文脈へ一般化するものではない。今回の別文脈評価では再利用が0件になるため、この方式の個人最適化の有効性は検証できない。

## 実験用起動設定

`MELTYPE_CONTEXT_ENDPOINT=http://127.0.0.1:18931/` を指定した候補brokerでのみ有効。localhost以外は拒否する。モデル・llama.cppは別プロセスで起動し、製品には自動インストールしない。待機中の結果をNative側から回収する処理も同じ候補内に含める。

自動実験は作業先で`./tools/context-eval/Run-ContextExperiment.ps1`を実行する。初回にモデルとCPU用runtimeを取得する場合は`-Download`を付ける。モデル・runtimeは固定したURLとSHA256で確認し、実験終了時にそのスクリプトが起動したserverだけを停止する。結果は`experimental-build/context-learning-results.json`、`context-native-results.json`、`zenz/environment.json`へ保存する。

Nativeの待機中の表示反映は、ビルド済み候補に対してbundled PowerShellから`tools/native-ime/Test-NativeUpstreamFeatures.ps1 -ContextEndpoint http://127.0.0.1:18931/`を実行して検証する。インストール・システム登録をせず、隔離した履歴とTSF文書を使う。

## モデルとruntimeの出典

- [zenz-v3.2-small Q5_K_M](https://huggingface.co/Miwa-Keita/zenz-v3.2-small-gguf)、モデルrevision `c67e03e07d215c869f591b274c1631170d3e11fe`。
- [azooKey/llama.cpp b4846](https://github.com/azooKey/llama.cpp/releases/tag/b4846)、Windows AVX2 CPU版。

今回取得した汎用llama.cpp b11630では`gpt2-small-japanese-char` tokenizerを認識できなかったため、対応するazooKey forkを使う。試験で成功した組み合わせを固定しており、他の版・GPUでの動作は確認していない。モデル・runtimeを製品の配布物へ同梱していない。

## 未検証事項

品質、CPU/GPUの実負荷、アプリごとの使用感は実行結果を確認してから記載する。現在のNative版が提供する入力欄の外部文脈は左側のみ。カーソル右側の既存文章の取得は今回追加しない。

## 変更前の長文評価

変更前にContextEvaluationと実zenzで20/50/80/100/101/200/400文字を比較した。候補は手作業で固定し、手掛かりが完成する前は採点しない。旧100文字境界と左128文字の切捨てを測定した結果はdocs/CONTEXT_LENGTH_RESULTS.md。現在の文脈幅とは異なるため、再実行した数値と混合しない。

これは長文のモデル・評価状態機械の対照実験で、実Google候補や実アプリの打鍵画面ではない。通常の180ms debounceと1500ms期限を使用する。要求・応答・採用・候補内正解の有無・意味が変わった対象語の系列・経過時間を保存する。共通の文字追加と対象語の変更を区別する。製品でのちらつきや確定値の保持は別途controllerテストで検証する。LLM上限を迂回した結果を本番経路の評価と混合しない。

別群direct-diagnosticに限り、旧100文字の状態機械の上限を通さず200/250/400文字を渡す。候補256文字上限・192生成token上限・1500ms期限は変更しない。evaluatorの呼出し回数はHTTP送信回数と同一視しない。新方式の再実行はtools/context-eval/Run-ContextLengthExperiment.ps1 -Clauses、実GoogleとTSFの確認は同スクリプトの-Native。集計はanalyze_clause_results.pyへ実行先を渡す。

## 先行する1000件の継続実験とGUI

805件で停止した実行では、801件目の`GitHub: `付き候補を先頭から生成させる要求が単独でも接続切断とserver終了コード3221226505を再現した。同じruntimeで、候補に共通する固定のASCII接頭部を出力の先頭へ事前入力し、日本語部分だけを生成させる要求は成功した。共通するASCII接頭部はpromptへ事前入力し、grammarから除き、応答へそのまま戻す。採用時の候補全体の照合と英字・記号保持は継続する。実モデルで801〜1000件目の200要求が失敗0件、候補内出力200件、接頭部保持200件だった。証跡はexperimental-build/mixed-prefix-repro。runtime内部の終了原因は未特定であり、途中や末尾に英字を含むすべての入力への対応を保証するものではない。

利用者の依頼により、1000件を独立したworkerで実行し、Windows Formsの進捗画面を表示する。チャットの終了後もworkerは継続する。画面を閉じてもworkerは止めず、停止ボタンは次のケースまでに停止する要求ファイルを作る。実行完了を待ってチャットから通知する運用にはしない。

20組の同音異義語、それぞれ2通りの意味、各5文脈の200意味例について、5種類の文脈配置・日英混在変種を作り1000件とする。1000件の独立した語義を検証するという意味ではない。別に各意味1例、計40例を履歴へ記録しない評価専用例とする。モデルの重みは固定し、採点は明示した正解との一致で行う。

1000件は順番にモデルへ実要求を送る。各履歴方式は、その時点までの自分の確定結果だけを学習する。機械的な模擬修正を25%のケースに割り当て、そこで誤りがあれば正解へ選び直し、それ以外は表示どおり確定する。取消予定イベントは履歴へ反映しない。全確定記録と明示修正のみの差や、誤確定の自己強化を比較するための仮定であり、人間の修正率を実測した値ではない。

処理0/100/300/1000件で40例の評価結果を比較する。実際の学習イベント数は方式と取消によって異なる。固定モデルへの40例の要求は最初に1回ずつ行い、同じモデル出力を各時点・各方式で共有する。従ってモデルへの要求は合計1040回。履歴効果の比較でモデル出力の揺れを混入させない。

GUIは評価件数、要求失敗、経過・推定残り時間、40例の方式別チェックポイント結果を表示する。JSONLへ各ケースを追記し、結果・進捗JSONは一時ファイルから置換する。失敗・停止時にも途中結果を残す。普段のIME・辞書・履歴、既存の26例のレポートは変更しない。

Windowsで進捗JSONを他のreaderが削除共有なしで開くと、置換が一時的にアクセス拒否になる。進捗保存は短く再試行し、引き続き保存できなければその更新を省略して評価を続ける。最終結果はresults.jsonと新しいterminal.jsonへ保存し、GUIはterminal.json、results.json、status.jsonの順に読む。進捗ファイルの競合をモデル要求の失敗や実験全体の失敗として扱わない。
